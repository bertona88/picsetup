# Independent AI review: PDK and compact models

2026-10-11. Perspective: photonic PDK/compact-model engineer. This is an independent AI assessment, not external human expert validation. Reviewed the current tree, required contracts, model/API/block code, relevant tests, and both Sketch/Compare screenshots. Historical test counts come from `HANDOFF.md`; I did not rerun the suite. I ran two focused, read-only probes.

**Verdict:** The import is honest and carefully engineered. The library is not yet useful enough to justify its prominence. It demonstrates that one real scattering table survives conversion and composition; it does not yet help someone choose between real components or make a physically coherent wavelength study. Preserve the discipline. Spend the next iteration on a tiny, internally understandable model family and its propagation assumptions, rather than collecting library names.

1. **Highest priority — propagation is the weakest link in the featured experiment. [Declared restriction; next capability.]** `src/blocks/index.ts` defaults every guide to constant `neff=2.4`, zero loss except the ring, and explicit lengths. `src/solver/solve.ts` uses that same constant in the phase. Consequently the guide group index equals its effective index in this model; importing a wavelength-dependent coupler does not fix the interferometer's propagation dispersion. The 10/20/30 µm comparison is legitimate hypothesis exploration, but “SiEPIC MZI” visually suggests a more coherent process model than it contains. Add an always-visible assumption summary: coupler dataset, guide model, loss assumption, and unknown modal/reference-plane compatibility. The upstream Simphony implementation already exposes a SiEPIC waveguide using `ne`, `ng`, and dispersion coefficients [S1]. That is a higher-value candidate than another unrelated component type.

2. **The interpolation artifact deserves an experiment, not only a footnote. [Declared numerical limitation.]** `evaluateDataset()` linearly interpolates complex Cartesian values in frequency. My probe of the bundled `data.json` found single-input midpoint power deficits of **1.2368–1.2858 percentage points** relative to the mean neighboring powers. At 1550 nm, `verification.json` gives 0.9837416 versus 0.9716001, equivalent to about **0.0539 dB** additional apparent insertion loss. This comparison is a numerical baseline, not the unknown true between-sample response. Tests correctly reproduce the interpolation; they cannot validate its physical fidelity. In `workbench-chromium.png`, the explanatory warning is much less prominent than the smooth curves. Offer raw-sample markers and a source-grid view before encouraging fine spectral conclusions. Evaluate phase-aware or delay-conditioned interpolation as a separately versioned method; do not silently replace, renormalize, or “repair” the source.

3. **A hard-coded adapter is an excellent first import and a poor library architecture. [Next capability.]** `registry.ts` enumerates `siepic-coupler`; `dataset.ts` imports one table; `catalog.ts`, `solve.ts`, exports, and `main.ts` identify that model directly. `datasetSigmaMax()` correctly relies on verified XOR symmetry, but that special norm cannot be reused for arbitrary models. Before a third dataset, introduce declarative model records with geometry, per-port mode identifiers, normalization, phasor convention, reference-plane status, source/license hashes, validity domain, interpolation version, and audit results. Unknown metadata must remain unknown. Derive a circuit's supported band from its actual selected models. Keep the existing specialized evaluator scoped to its dataset; use general full-matrix audits for new families. This is structured data plumbing, not a reason to implement a universal PDK importer.

4. **Selection currently exposes a brand more clearly than the scientific choice. [Product/API gap, plus two small defects.]** The screenshots make recipes and comparisons approachable; the main model selector offers “Open dataset · SiEPIC,” with fixed geometry described only after selection. A useful chooser should preview through/cross/reflection spectra, native sampling, geometry, provenance, and qualifications before insertion. TE0 versus source “TE mode 1” is correctly distinguished in the contract, but labels alone do not establish physical mode matching. Concrete inconsistencies: `propagation()` advertises `neff.min=0`, while `parameters()` rejects zero; the built API probe reproduces this. Also the dataset README/contracts round the weighted neighboring power to **0.9834**, while the audit says **0.9837416**. Neither is a solver defect. The inspector's “Optical length” label is also ambiguous: its value is physical guide length multiplied by index in the solver; call it “Guide length.”

Three bounded experiments would establish a useful direction:

- **First: dispersion changes the answer.** Audit one upstream SiEPIC strip-waveguide coefficient set, with explicit geometry and source conditions, and compare the existing MZI using constant index versus dispersive propagation. Keep loss independently declared. Success: independent complex-field agreement within the project's existing numerical tolerance, verified group-delay/phase derivative, recorded validity band, and a saved notebook explaining the fringe-spacing change. Do not claim physical modal compatibility merely because both sources say SiEPIC.
- **Second: choose an actual coupler.** Curate three discrete coupling lengths, such as 5/10/20 µm at 200 nm gap, from the documented SiEPIC family [S1]. Audit each exact file and license, retain complete matrices, and compare splitting and MZI behavior on their common band. Success: model selection requires no JSON edits; export/reopen preserves exact identities and audits; unsupported geometries cannot be entered. Availability and quality of those exact files at the intended pin remain **unverified** in this review.
- **Later: one SiPANN geometry study.** Generate bounded tables offline rather than embedding another Python ecosystem. SiPANN documents geometry-dependent couplers and waveguides; its v1.4.0 SCEE documentation states explicit training-domain limits [S2]. The repository currently identifies 2.0.2 and MIT licensing [S3]; version agreement and runtime behavior are **unverified**. Success requires a pinned executable environment, explicit port/phase mapping, domain rejection, and agreement with the producer at every exported sample. This experiment should follow, not delay, the SiEPIC slice.

**Preserve:** exact bytes and both MIT notices, one-time conjugation, all sixteen entries, full-matrix passivity evidence, separate model-supplied-power accounting, independent NumPy references, and zero mandatory runtime services. **Stop:** treating more catalog entries or a SAX integration as scientific validation. SAX is a circuit engine accepting model functions [S4]; it is useful as an interchange/oracle target, not a source of automatically qualified device physics.

**Recommended next slice:** the dispersive-waveguide MZI notebook, accompanied by the assumption summary and raw-grid visibility. It strengthens the experiment already on screen before broadening the shelf.
